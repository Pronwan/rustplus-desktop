## 1. Rebuild Contract

The rebuilt application must behave as a modern client-side Rust plant-genetics assistant with three routes:

1. **Calculator** `/`
2. **Guide** `/guide`
3. **Recipes** `/recipes`

The Calculator is the primary product. It accepts lists of six-character plant gene strings, searches possible crossbreeding combinations in Web Workers, scores and ranks resulting genetics, supports one to three generations, shows alternate breeding plans, explains center/surrounding plants, highlights source plants in the input, persists optional gene-set history, and can read genes from the Rust game window through screen capture + OCR on supported desktop browsers.

The rebuild must preserve the behavior described below, but it does **not** need to preserve Vue 2 or Vuetify 2. A React/TypeScript implementation is appropriate as long as behavioral compatibility is maintained.

### Non-negotiable compatibility targets

- Six gene slots per plant.
- Valid gene alphabet: `G`, `H`, `Y`, `W`, `X`.
- Crossbreeding weight model: green genes `G/H/Y = 0.6`; red genes `W/X = 1.0`.
- Exhaustive combination search, split across workers.
- Optional repeated source plants in a combination.
- Configurable surrounding-plant range.
- Configurable scoring and minimum tracked score.
- Multi-generation calculation up to 3 generations in current UI.
- At most **3 retained breeding maps per identical result genotype**.
- Result sorting semantics described in §8.
- Conditional center-plant simulation.
- Tie handling and chance propagation.
- Partial progressive result delivery while calculation is still running.
- Calculation ETA and per-generation progress.
- Screen-capture OCR workflow with two configurable capture regions.
- Input history with a maximum of 200 saved sets.
- Functional/analytics/advertising consent separation.
- Dark/light UI mode.
- Responsive desktop/mobile layout.
- Current plant selector is cosmetic/contextual only: it does **not** modify genetic calculation.

# 6. Domain Model

## 6.1 Gene enum

```ts
type GeneType = 'G' | 'H' | 'Y' | 'W' | 'X';
```

Semantic categories:

- `G`, `H`, `Y` = green genes.
- `W`, `X` = red genes.

Game-facing meanings displayed in the Guide:

- `G`: growth-rate benefit.
- `Y`: yield benefit.
- `H`: environmental-hardiness benefit.
- `W`: undesirable increased water consumption.
- `X`: undesirable/no benefit.

## 6.2 Crossbreeding weights

```ts
GREEN_GENE_WEIGHT = 0.6
RED_GENE_WEIGHT   = 1.0
```

`Gene.getCrossbreedingWeight()` returns 0.6 for `G/H/Y`, otherwise 1 for `W/X`.

## 6.3 Sapling

```ts
class Sapling {
  genes: Gene[];            // exactly 6 for valid plants
  generationIndex: number;  // user-provided = 0; generated starts at 1
  index?: number;           // original source-list position
}
```

Behavior:

- Construct from gene string, gene list, or empty.
- `addGene(gene)`.
- `numberOfGs()`.
- `numberOfYs()`.
- `numberOfHs()`.
- `getScore(geneScores)` sums configured score per gene and rounds to 2 decimal places.
- `toString()` joins six types.
- `clone()` shallow-clones genes and preserves generation/index.

## 6.4 GeneticsMap

A `GeneticsMap` is one concrete breeding plan for a resulting plant.

```ts
class GeneticsMap {
  resultSapling: Sapling;
  baseSapling?: Sapling;                    // required center plant, if any
  baseSaplingVariants?: GeneticsMapGroup;   // how to create that generated center
  crossbreedingSaplings: Sapling[];         // surrounding plants
  crossbreedingSaplingsVariants?: GeneticsMapGroup[];
  score: number;
  chance: number;                           // probability local to this breeding step
  sumOfComposingSaplingsGenerations: number;
  tieWinningCrossbreedingSaplingIndexes?: number[];
  tieLosingCrossbreedingSaplingIndexes?: number[];
}
```

Methods:

- `clone()` deep-enough clones nested model structures.
- `getChanceProduct()` recursively multiplies local chance by dependency-map chances, representing total path probability.

## 6.5 GeneticsMapGroup

Groups alternative breeding plans that produce the same result genotype.

```ts
class GeneticsMapGroup {
  resultSaplingGeneString: string;
  mapList: GeneticsMap[];
}
```

At most **3** maps are retained per group after sorting.

# 7. Exact Crossbreeding Algorithm

This section is the critical behavioral contract.

## 7.1 Core concept

For a proposed set of surrounding plants, crossbreeding is calculated independently for each of the six gene columns.

At each column:

1. Group surrounding genes by gene type.
2. Sum each contributing gene’s crossbreeding weight.
3. Find the highest total weight.
4. Keep only gene type(s) whose total equals the maximum.
5. Track which surrounding plant indexes contributed to the winning/tied types.
6. Potentially compare the result with the center plant.

## 7.2 Combination validity pruning

A surrounding-plant combination is rejected before creating result plants when either condition occurs:

### Rule A — more than one recognizable tie

For each of six columns, after summing surrounding weights:

- If more than one gene type ties for the highest total **and** that total is greater than the red-gene weight (`> 1.0`), count it as an early definitive tie.
- If more than one such tied column exists, reject the combination.

This keeps the result branching manageable and reflects the app’s intended reliability model.

### Rule B — every selected surrounding plant must contribute

Collect every surrounding plant index that contributes to at least one winning/tied gene column.

If the number of contributing indexes is not equal to the selected surrounding-plant count, reject the combination.

This intentionally discards combinations containing a plant that does not influence the outcome.

## 7.3 When the center plant must be checked

The algorithm conditionally tests concrete center plants.

A center check is required only when:

- the number of surrounding plants is `<= 5`, **and**
- at least one winning surrounding-column total is `<= 1.0`.

If no center check is needed, the output can be computed solely from surrounding winners.

If a center check is needed:

- consider each source plant **not already present in the surrounding set** as a potential center plant;
- compute resulting genes against that center;
- score/filter each output.

## 7.4 Center-vs-surrounding rule

For each gene column, if a center plant is being evaluated:

```ts
useCenterGene = centerGeneWeight >= winningSurroundingTotalWeight
```

The comparison uses `>=`, so a center gene survives when it ties the surrounding winning total.

If the center does not survive, use the winning surrounding type or branch on a tied winner.

## 7.5 Tie result branching

For one definitive tied column:

- Clone the partially built result once for each tied winning gene type.
- Add the corresponding candidate gene to each clone.
- Record which surrounding plant indexes contribute to the branch’s winning gene.
- Record the surrounding indexes contributing to other tied gene types as tie losers.

If a second definitive tied column is encountered, discard the entire combination.

## 7.6 Probability

For the result list produced by one candidate breeding setup:

```ts
chance = 1 / potentialResults.length
```

Therefore a two-way tie produces a local 0.5 probability for each branch.

For multi-generation maps, displayed/ordering total probability uses `getChanceProduct()` to multiply dependency probabilities down the breeding tree.

## 7.7 Ignore results already owned

Before accepting a potential output:

- Convert all source saplings to genotype strings.
- Discard any output genotype already present in the source set.

## 7.8 Score filter

For each remaining output:

```ts
score = resultSapling.getScore(options.geneScores)
```

Accept only:

```ts
score >= options.minimumTrackedScore
```

## 7.9 Generation-composition cost

The map stores:

```ts
sumOfComposingSaplingsGenerations =
  sum(generationIndex of surrounding plants) +
  (centerPlant ? centerPlant.generationIndex : 0)
```

This value participates in result-plan sorting, favoring plans whose dependencies are simpler/earlier-generation.

# 8. Combination Enumeration, Workers, Sorting, and Multi-Generation Search

## 8.1 Combination search space

For each surrounding-plant count `k` from configured minimum through maximum:

- Without repetitions: standard `n choose k` combinations.
- With repetitions: combinations with replacement, count `C(k+n-1, k)`.

`maxPositionsCount`:

```ts
withRepetitions
  ? maxCrossbreedingSaplings
  : min(itemsCount, maxCrossbreedingSaplings)
```

The app enumerates combinations by maintaining a monotonically ordered array of source indexes and incrementing/resetting indexes rather than materializing the entire combination space in memory.

## 8.2 Later-generation mandatory plants

For generation > 1, newly generated plants are prepended to the source array and `generationInfo.addedSaplings` records their count.

Enumeration restricts the first combination index so every later-generation combination contains at least one newly generated plant. This avoids recalculating combinations that were already exhaustively evaluated in the previous generation.

## 8.3 Work chunk planning

Current v3 constant:

```ts
WORK_CHUNKS_PER_WORKER = 50
```

If `numberOfWorkers === 1`, create one work chunk.

Otherwise:

```ts
numberOfWorkChunks = numberOfWorkers * 50
```

A dedicated chunk-planner worker computes `WorkChunk[]` containing:

```ts
interface WorkChunk {
  startingPositions: number[];
  combinationsToProcess: number;
  allCombinationsCount: number;
}
```

Chunks are distributed round-robin across calculation workers:

```ts
workChunkIndex % numberOfWorkers === workerIndex
```

## 8.4 Calculation worker progress

Each calculation worker receives:

- source saplings;
- its assigned `workChunks`;
- generation info;
- options.

It emits:

- number of combinations processed since last report;
- partial grouped map results.

Worker-serialized objects have prototypes restored on the main thread so model methods remain callable.

## 8.5 Partial result organization

For each incoming result genotype:

1. Append maps to its existing group or create group.
2. Sort maps using `resultMapsSortingFunction`.
3. Keep only the first 3 maps.
4. Repair prototypes after worker structured-clone serialization.

## 8.6 Sorting maps that produce the same genotype

Preferred order:

1. Lower result `generationIndex`.
2. Higher local `chance`.
3. Lower `sumOfComposingSaplingsGenerations`.
4. Fewer surrounding plants.

## 8.7 Sorting result genotype groups

Compare each group’s first/best map. Preferred order:

1. Higher `score`.
2. Higher recursive chance product.
3. Lower generation index.
4. Lower sum of composing generations.
5. Lexicographically smaller genotype string as final deterministic tie breaker.

## 8.8 Progressive UI update timing

Current orchestrator constants:

```ts
PARTIAL_RESULT_INCREMENTAL_UPDATE_FREQUENCY_MS = 1000
ESTIMATION_TIME_UNIT_MS = 10000
ESTIMATION_SENT_AFTER_MS = 1000
```

Partial updates are initially eligible after 1 second; after each partial result update, the next interval increases by another 1 second. In effect, result UI refreshes become progressively less frequent as a long search continues.

## 8.9 ETA

Maintain recent processing stats from the last 10 seconds:

```ts
{ timestamp, combinationsProcessed }
```

After at least 1 second of calculation:

```ts
avgCombinationsPerMs =
  sum(recent combinations) /
  min(10000, elapsedMs)

estimatedMsLeft =
  (allCombinations - processedCombinations) /
  avgCombinationsPerMs
```

The UI throttles global ETA-store updates to roughly every 250 ms.

## 8.10 Orchestrator event contract

```ts
type SimulatorEventType =
  | 'PROGRESS_UPDATE'
  | 'PARTIAL_RESULTS'
  | 'DONE_GENERATION'
  | 'DONE';
```

Payload fields can include:

- `generationIndex`
- `progressPercent`
- `estimatedTimeMs`
- `mapGroups`

## 8.11 Selecting plants for the next generation

After a generation finishes, if another generation is configured:

1. Consider only maps whose result plant belongs to the generation that just completed.
2. Determine gene-column quality already available in the source population using configured gene scores.
3. Prefer result plants that improve the weakest/least-covered columns.
4. Within candidates, favor the best map ordering.
5. Add up to `numberOfSaplingsAddedBetweenGenerations` selected results.
6. Prepend selected generated plants to existing source plants.
7. Run the next generation with `addedSaplings` count so enumeration requires at least one new plant.

If no useful generated plants can be selected, finish early.

## 8.12 Skip generation

“Skip” while calculating:

1. Terminate active calculation workers.
2. Treat current accumulated partial maps as the completed generation.
3. Emit generation-done data.
4. Select best candidates for next generation.
5. Continue if possible.

The UI warns that skipping can save time but can miss results.

## 8.13 Cancel

Cancel terminates all active workers and returns UI to non-simulating state. ETA and title are reset.

# 10. Gene Input UX

## 10.1 Raw format

One plant per line, exactly six characters.

Example safe input shape:

```text
GYXWHH
XWHYYG
GHGWYY
```

Allowed characters only: `G H W Y X`.

## 10.2 Validation rules

The current form enforces:

1. Every non-empty line must contain exactly 6 valid genes.
2. Input cannot be empty.
3. At least two plants are required.

Regex behavior accepts trailing newlines but not incomplete rows.

## 10.3 Input normalization

On each input:

- Convert to uppercase.
- Remove every character other than `G/H/W/Y/X/newline`.
- Remove a leading newline.
- Preserve caret position as closely as possible after cleanup.

On blur:

- Collapse repeated blank lines into one newline.
- Deduplicate identical genotype rows while preserving first occurrence order.
- Revalidate.

Invalid gene highlighting becomes stronger if the input is not focused or no typing has occurred for 2 seconds.

## 10.4 Query-string import

On mount:

```text
?genes=AAAAAA,BBBBBB,...
```

is parsed as comma-separated genotype entries and converted to newline-separated input.

Only valid gene characters survive normal input sanitization.

## 10.5 Keyboard feedback

Accepted keys include gene letters plus editing/navigation keys. Other typed keys can trigger the “wrong key” audio when sound is enabled.

## 10.6 Visual preview and numbering

- Render each row as a six-gene chip/slot representation.
- Show source numbering (`#1`, `#2`, ...).
- Numbering can visually emphasize periodic boundaries in larger lists.
- Newly OCR-scanned gene rows animate and scroll into view when necessary.

## 10.7 Highlighting required source plants

When a user selects a result map:

- Locate each surrounding source genotype in the original input list.
- Overlay a highlight alongside that input row.
- If the result needs a concrete center/base plant, highlight that row with a distinct base style.
- Avoid highlighting the same source row more than once.

```ts
    height: { ideal: 1080 },
    frameRate: { max: 30 }
  },
  audio: false
})
```

4. Initialize OCR workers.
5. Create an off-DOM video element and attach captured stream.
6. On `loadedmetadata`, begin scanning and emit analytics start event.
7. If the video track emits `ended`, stop capture.
8. Play the video.

Capture-request rejection is silently ignored by the service; UI should return gracefully.

## 12.3 OCR workers

The scanner creates **one OCR worker per gene slot per capture region**.

Current region count = 2 and genes per region = 6, so normal target = **12 Tesseract workers**.

Initialization procedure per worker:

1. `createWorker` with explicit worker/core/lang paths.
2. `load()`.
3. `loadLanguage('eng')`.
4. `initialize('eng')`.
5. Set page segmentation mode to `SINGLE_CHAR`.

If worker setup fails:

- terminate any partially initialized worker;
- delete IndexedDB database `keyval-store`;
- recursively retry setup.

## 12.4 Scan cadence

Constant:

```ts
SCAN_INTERVAL_MS = 200
```

The loop uses `requestAnimationFrame`, waits for a full `scanFrame()`, then schedules another pass after 200 ms while active.

## 12.5 Convert normalized region to pixels

For each region:

```ts
xPx = round(videoWidth  * TOP_LEFT_X)
yPx = round(videoHeight * TOP_LEFT_Y)
widthPx = round(videoWidth * WIDTH)
normalizedHeight = WIDTH * HEIGHT_TO_WIDTH_RATIO
heightPx = ceil(videoHeight * normalizedHeight)
geneWidthPx = round(widthPx * GENE_WIDTH_TO_WIDTH_RATIO)
```

## 12.6 Split a region into six gene crops

1. Draw the capture region into an internal canvas.
2. `geneCount = 6`.
3. Total width occupied by six gene crops = `geneWidthPx * 6`.
4. Remaining width is divided across 5 gaps.
5. Extract six `ImageData` crops with `getImageData`.
6. Send a region preview with gap areas darkened at 35% opacity.

## 12.7 Image preprocessing before OCR

Each gene crop is converted through the current image pipeline:

1. greyscale;
2. invert;
3. normalize;
4. scale by 2;
5. convolution sharpen kernel:

```text
 0   -0.5  0
-0.5  4   -0.5
 0   -0.5  0
```

6. contrast `0.5`;
7. convert to PNG base64;
8. OCR with the worker assigned to that region+gene slot.

OCR text processing:

- remove whitespace;
- uppercase;
- accept only exactly one character matching `[GHYWX]`;
- otherwise return null.

## 12.8 Recognized plant

For each region, concatenate the six OCR outputs, replacing nulls with empty strings.

Only emit a plant when the final string matches:

```regex
^[GHYWX]{6}$
```

Event:

```text
SAPLING-FOUND
```

The gene input ignores a scan if that exact genotype is already present.

Observed current event strings:

- `STARTED`

- `PREVIEW`
- `SAPLING-FOUND`

## 12.10 Scanner calibration UI

Preview panel contains two region canvases:

- Inventory Region.
- Planter Region.

Gear toggles configuration controls.

Per-region controls:

- Move up/down/left/right.
- Zoom in/out.

# 23. Recipes Page Engine

The current v3 bundle embeds a recipe array and turns it into an expanded view model on component creation.

## 23.1 Generic schema

```ts
interface Ingredient {
  item: string;
  quantity: number;
}

interface Recipe {
  item: string;
  ingredients: Ingredient[];
  output: {
    item: string;
    quantity: number;
  };
}

interface ExpandedRecipe extends Recipe {
  baseIngredients: Ingredient[];
}
```

## 23.2 Item image slug

Current helper converts recipe/item name to:

```ts
`/img/items/${name
  .replaceAll(' ', '-')
  .replaceAll('.', '_')
  .toLowerCase()}.webp`
```

## 23.3 Recursive expansion

The component creates a lookup map `recipeByItem`.

Conceptual algorithm:

```ts
function expand(itemName): Ingredient[] {
  const recipe = recipeByItem[itemName]

  if (!recipe) {
    return [{ item: itemName, quantity: 1 }]
  }

  const base: Ingredient[] = []

  for (const ingredient of recipe.ingredients) {
    const nested = expand(ingredient.item)

    for (const n of nested) {
      base.push({
        item: n.item,
        quantity:
          n.quantity * ingredient.quantity / recipe.output.quantity
      })
    }
  }

  return base
}
```

Then consolidate equal base item names by summing quantity.

The production implementation computes `baseIngredients` for every recipe at component creation and renders expandable rows/cards.

## 23.4 Safe data categories observed

The data set includes ordinary food/mixing/resource recipes such as berry teas and other non-sensitive crafting ingredients. It also contains some weapon/ammunition-related game recipes; those exact entries are intentionally not reproduced here. Keep the recipe system data-driven so any permitted dataset can be supplied independently from the UI/engine.

# 27. Error Handling and Edge Cases

Implement intentionally, not as afterthoughts.

## Input

- Empty input => invalid.
- One plant => invalid.
- Incomplete 1–5 character row => invalid.
- Any non-gene character is stripped during typing.
- Duplicate rows are deduplicated on blur and before calculation.
- Query-string genes may be malformed; run through the same validation/sanitization path.

## Options

- Stored worker count can exceed current machine core count; clamp.
- Bad/old options cookie should be schema-validated in a rebuild; current bundle assumes parsable JSON, but the rebuild should fail to defaults safely.
- Never allow min surrounding count > max surrounding count after UI normalization.

## Calculation

- No useful maps => completed empty results state, not an exception.
- If next-generation candidate selection returns no plants, terminate calculation early.
- Cancel/skip must terminate both chunk planner and calculation workers.
- Ignore late worker messages from a cancelled run; recommended rebuild adds a `runId` token to prevent stale-message races.

## Scanner

- User denies screen share => stay idle.
- Track ends externally => stop scanning.
- OCR initialization fails => clear Tesseract cache and retry, but rebuild should add a bounded retry + visible error rather than unbounded recursion.
- OCR invalid character => ignore that frame.
- Partial six-gene scan => ignore that frame.
- Duplicate recognized plant => do not append.
- Missing canvas context => fail preview gracefully.
- Calibration must remain within normalized screen bounds.
- HDR/conflicting visual settings can reduce OCR quality; provide calibration preview rather than depending on one fixed screen resolution.

## Persistence

- Bad JSON in localStorage should be ignored and reset safely.
- Functional-consent revocation must clear saved sets/scanner regions/options as documented.
- Multi-tab `storage` events update history list.

# 28. Performance Requirements

The calculation can be combinatorially expensive. Preserve the original performance model and improve it where safe.

## Must do

- Run exhaustive search off the main thread.
- Do not materialize all combinations at once.
- Chunk the search space.
- Stream partial results.
- Retain only top 3 maps per genotype continuously to cap memory growth.
- Freeze or clone UI snapshots so worker result accumulation does not cause accidental reactive deep mutation.
- Keep map-model data serializable.

## Recommended improvements

- Cap worker count to a sensible UI-selectable range even when `hardwareConcurrency` is extremely high.
- Add run IDs/cancellation tokens.
- Use transferable structures only if profiling proves useful.
- Replace class prototype repair with plain serializable domain DTOs + pure functions where possible.
- Cache genotype string and score on immutable result nodes during a run.
- Unit-test combination counts against reference implementation.

# 29. Testing Contract

## 29.1 Gene model tests

- green types return 0.6.
- red types return 1.
- six-gene round-trip string conversion.
- score correctly sums configurable weights and rounds to 2 decimals.
- G/Y/H counters correct.

## 29.2 Crossbreeding tests

Create deterministic fixtures for:

- one clear winning type in all six columns;
- center gene survives when its weight equals surrounding total;
- surrounding gene wins when total exceeds center;
- one tied column branches and probabilities sum to 1;
- more than one definitive tied column is rejected;
- combination where one selected surrounding plant contributes nowhere is rejected;
- output equal to existing source genotype is excluded;
- result below minimum tracked score is excluded;
- specific center plant required vs arbitrary center case.

## 29.3 Combination tests

- without-replacement count matches binomial sum.
- with-replacement count matches multiset-combination sum.
- every combination enumerated exactly once.
- later generation only enumerates combinations containing at least one newly added plant.

# 30. Recommended Modern Rebuild Improvements Without Changing Core Behavior

These are improvements, not required compatibility quirks.

1. **Type all worker messages with discriminated unions.**
2. **Use pure DTOs rather than repairing prototypes after worker serialization.**
3. **Bound OCR initialization retries** and report a clear error.
4. **Add robust persistence migrations** for `options-vN` and saved sets.
5. **Add a run ID** to every worker request/response to discard stale messages after cancel/restart.
6. **Add worker failure handling** and fallback to fewer workers if spawning fails.
7. **Use `IntersectionObserver`** instead of manual scroll/resize viewport checks.
8. **Use `ResizeObserver`** for stacked-card height and SVG connector geometry.
9. **Honor reduced motion.**
10. **Improve accessibility** as described in §24.12.
11. **Separate content from mechanics**: Guide articles and Recipes should be typed data, not giant inline render templates.
12. **Make analytics fully optional** through a no-op adapter.
13. **Add Web Worker unit/integration tests** against a single-thread reference engine.
14. **Add performance instrumentation** around combinations/second and memory use.
15. **Keep the calculation engine deterministic** so a known input/options snapshot gives reproducible sorted result order.

```text
PERSISTENCE
```
